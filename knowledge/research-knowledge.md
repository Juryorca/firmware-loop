## 认证/授权：对象级 owner 与权限语义

**适用**：管理 API 用 id/hash 定位对象，list 有过滤，但 get/edit/delete 可能漏 owner/scope 检查。

**识别**：同一资源的 list、get、update、delete 是否共用同一套 owner/scope 判定？对象是否有 owner 字段？攻击者能否从正常渠道拿到 id（分享链接、二维码、响应字段）？

**成立条件**：受限主体真实存在；管理动作确实改变他人对象状态；不能只证明“能查看/下载”。ID 可预测或可枚举不等于可利用，要算枚举窗口、速率和泄露渠道。

**排除/降权**：对象没有 owner 概念；该操作本就是 capability 模型允许的；UI 与 API 都把 edit/delete 限制给 owner；只有 view 权限而没有管理动作。

**判断要点**：list 的安全不等于对象级安全；“知道 id”与“能管理”必须分开证明。来源：旧 `vuln-patterns` 的 IDOR/owner 条目与 `misreports` 的可预测 id 条目。

## 认证/授权：代理、转发头与默认拓扑

**适用**：自研 httpd/守护进程信任 `X-Forwarded-For`、`X-Real-IP`、`Host` 等客户端头，或后端只靠 loopback/内网隔离。

**识别**：默认启动后谁监听 0.0.0.0/公网口？前置代理是否追加头，后端取第一个还是最后一个 token？有没有“代理未启动/特性开关/启动失败”导致后端直连的非默认态？内部端口是否真的只绑 loopback？

**成立条件**：客户端可控头能到达后端且被当作可信来源；或非默认态下预认证面可达；并造成权限/来源判断变化。

**排除/降权**：默认拓扑下后端只绑 loopback，代理会覆盖/追加并取可信 token；攻击者没有能力制造非默认态；只是协议内回调/正常代理行为。

**判断要点**：先画默认前端拓扑，再谈预认证可达；非默认态要明确标注。来源：旧案例中的 XFF/Host/中继信任与 setup 态条目。

## 认证/授权：门的位置、状态与管理员等价

**适用**：CGI/action 分派、初始化端点、内部集成端口、Scope/中间件缺失、admin 组命令注入。

**识别**：认证/CSRF 门在分派表之前还是之后？setup/onboarding 状态是否开放了超出初始化需要的端点？管理动作是否要求 admin/root 等价角色？派生连接是否继承了主会话身份但没有自己的来源绑定？

**成立条件**：未认证/低权主体能到达本应受保护的操作；或状态/角色判断被绕过；并且有实际能力增益。

**排除/降权**：门要求 admin 且该角色在本产品已 root 等价；内部端口默认不可从攻击面到达；setup 态只开放设计必需的少数端点；只是“门存在但顺序不同”而没有可达路径。

**判断要点**：报告命令注入/越权前先问“门后面是谁、攻击者原本能做什么”。来源：旧 `vuln-patterns` 的 dispatch/setup/内部端口条目与 `misreports` 的 admin 等价条目。

## 命令与参数注入：从输入到 shell 的边界

**适用**：CGI/守护进程把请求参数、文件名、路径、header 拼进 `system()`/`popen()`/`fork_call()`。

**识别**：追踪完整数据流：输入源 → 校验/规范化 → 拼接格式串 → shell。单引号包裹不等于安全（值里可有 `'`）；自定义转义 helper 可能漏反引号、换行、`$()`；路径/对象前置校验可能降低可利用性但不等于无注入。

**成立条件**：攻击者可控数据进入 shell 解释层，且能执行命令/改变参数边界；最好有 benign vs payload 差分和 marker 落盘。

**排除/降权**：输入来自管理员配置且分支值域锁死；参数只能是已存在对象/合法路径且无法注入分隔符；sink 存在但无可控插值源；需要 admin 且无权限增益。

**判断要点**：`exec/system` 的存在只是候选；先证明插值数据源和转义边界。来源：旧 `vuln-patterns` 的命令注入/转义 helper 条目与 `misreports` 的 exec/sink 条目。

## 解析器与内存安全：长度、边界、部分覆盖

**适用**：自定义协议/文件格式、URL/文件名入包、XML/JSON 解析、固定栈缓冲、`memcpy`/长度字段。

**识别**：长度来自请求内偏移之差、外部长度字段还是内部常量？是否有整数下溢/符号扩展/截断？固定栈缓冲的拷贝上限是否真的与输入长度无关？解析器是否在未认证输入上做实体展开/递归？部分覆盖是否足以控制返回地址/函数指针？

**成立条件**：可控长度/内容导致越界读写、控制流改变、资源耗尽或信息泄露，并有可复现信号。

**排除/降权**：越界写被后续密文/校验原样还原；读宽与游标前进量相等，被 `cursor==end` 抵消；限制“不能含 NUL”使链不可叠但仍可低位覆盖时要单独评估；只有崩溃没有可达性/权限影响时按 DoS 降级。

**判断要点**：先做边界算术和调用约束，再谈“栈溢出”；崩溃不是自动漏洞。来源：旧 `vuln-patterns` 的 memcpy/整数/XML 条目与 `misreports` 的块密码/RDLENGTH/部分覆盖条目。

## 路径、URL 与 Host 解析

**适用**：密码重置、邮件链接、重定向、代理路由、Host 校验、文件路径拼接。

**识别**：解析器是否在首个 `:`、`@`、`?`、`#` 或反斜杠处截断？校验用的字符串与实际回填/跳转的字符串是否是同一个？URL userinfo（`http://allowed:port@attacker/`）是否会被误判为 allowed？路径规范化与文件打开是否使用同一结果？

**成立条件**：校验结果与实际使用结果不一致，导致跳到攻击者域、读取越界路径或绕过 allowlist。

**排除/降权**：校验和消费使用同一规范化值；只影响管理员可控配置；目标没有敏感动作或数据。

**判断要点**：解析差异要比“看起来像 SSRF/重定向”更重要。来源：旧 `vuln-patterns` 的 URL host 截断条目与 `misreports` 的 Host/代理条目。

## 速率限制、锁定与拒绝服务

**适用**：登录、认证、限流器、连接池、XML/JSON 解析、内存分配。

**识别**：限流状态是进程全局还是按来源/账号？阈值/衰减是否符合设计？失败尝试能否填满状态并影响其他来源？未认证解析器能否用实体膨胀/大分配耗尽资源？

**成立条件**：攻击者能以低成本造成跨主体/不可逆影响，或绕过本应存在的速率控制。

**排除/降权**：按设计拒绝服务且能自愈；只影响攻击者自己的会话；需要管理员/本地权限；只是“可复现”但没有跨主体影响。

**判断要点**：先量化时间窗、并发和恢复；不要把设计内的锁定/退避报成漏洞。来源：旧 `vuln-patterns` 的认证限流条目与 `misreports` 的限流/DoS 条目。

## 误报判据：能力、证据与设计内行为

**适用**：看到 sink、200 响应、panic、配置泄露、默认密钥、可预测 id、客户端自报身份时。

**识别**：攻击者能拿到什么合法流程拿不到的能力？证据是否证明“可利用”而不只是“存在”？响应状态码是否把未授权放在 body？配置值是否出厂静态默认？默认密钥是否真的能过解密后的验收门？id 可预测是否有枚举窗口和泄露渠道？

**成立条件**：有明确的权限/数据/状态增益，且能排除设计内行为。

**排除/降权**：只证明 sink/崩溃/配置存在；管理员等价；输入来自管理员配置；协议内回调；默认值没有实际安全后果；历史案例只能作参考。

**判断要点**：先问“所以攻击者能做什么”，再决定是否上报。来源：旧 `misreports` 的反例库整体。

## 工具判据：qemu-user 直调 CGI 必须补齐 httpd 注入的环境

**适用**：绕过真实 httpd，用 `qemu-<arch> -L rootfs <cgi>` 直接跑 CGI 做动态验证。

**判据**：qemu-user 只负责 ELF/库搜索，不会自动补齐 httpd 的 CGI 环境变量（`SCRIPT_FILENAME`、`SCRIPT_NAME`、`PATH_INFO`、`PATH_TRANSLATED`、`GATEWAY_INTERFACE` 等）。缺失时，目标里未检查的 `getenv()` 可能返回 NULL，导致 `strstr/strlen` 等崩溃。

**排除/降权**：做 A/B——补上/去掉该 env，若崩溃随 env 变化而非 payload 变化，就是仿真产物，不是载荷触发的内存破坏。

**操作要点**：先按真实 httpd 的 CGI 契约补齐环境，再逐项只改 payload；不要用一次崩溃直接写 finding。来源：旧 `tool-quirks` 的 qemu CGI 条目。

## 工具判据：binwalk 的“提取成功”不等于有效

**适用**：固件解包后准备分析 rootfs。

**判据**：binwalk 返回成功但产出很少（例如少于 3 个有效文件）通常意味着格式未被正确处理；应换 `unblob` 重试，并同时检查两个输出目录。两个工具的产出都要看，不能只信其中一个的“完成”。

**排除/降权**：提取器缺失会导致 unblob 静默失败；缺哪个外部提取器按对应格式补齐/记录，不要把它当成“固件没有内容”。

**操作要点**：保留两个输出目录、文件数与失败原因；对加密/非标格式再走静态魔数/解密例程。来源：旧 `tool-quirks` 的 binwalk/unblob 条目。

## 工具判据：qemu-user 的 `-L` 不改变绝对路径命名空间

**适用**：固件 CGI/守护进程访问 `/var/run`、`/tmp` 等绝对路径，或 `system()`/`popen()` 触发子进程。

**判据**：`qemu-<arch> -L rootfs` 只改解释器/库搜索路径，不改绝对路径命名空间；目标写 `/var/run/x` 仍可能落到宿主，导致权限失败/静默走 else 分支。qemu-user 也不会翻译 `execve`，不能据此断言“设备执行了命令/读到了设备文件”。

**操作要点**：需要设备侧行为时用 chroot、容器、`binfmt_misc` 或 bwrap 把根目录与 `/var/run` 等挂载点隔离；补 `--tmpfs /var/run` 之类可写目录，注意固件 `/tmp` 可能是软链。

**排除/降权**：仅验证“确实发起了 system/exec”可用 qemu-user；要证明执行落在目标 rootfs 必须用 chroot/容器等。来源：旧 `tool-quirks` 的 qemu/bwrap 与 `AGENTS` 的 execve 边界。

## 工具判据：AFL qemu-trace 必须与 guest 架构匹配

**适用**：无源码二进制 fuzz，使用 `afl-fuzz -Q`。

**判据**：`afl-qemu-trace` 是分架构产物；用 x86-64 tracer 跑 aarch64 guest 可能不报错但 coverage 为 0。先确认 tracer 与目标架构一致；用 `AFL_PATH` 指向正确产物，跑 `afl-showmap` 看是否有 tuples。

**排除/降权**：`-Q` 静默 0 tuples、只打印 Executing、或 tracer 与 guest 架构不符，都是环境/工具问题，不是“目标没有输入面”。

**操作要点**：构建/选择对应架构 tracer，先用小输入冒烟验证 tuple；不要把 0 coverage 当研究结论。来源：旧 `tool-quirks` 的 AFL qemu 模式与 `AGENTS` 环境清单。

## 工具判据：IDA MCP 无头端点需要 GUI 事件循环

**适用**：用 IDA MCP 做批量反编译/查询，希望无头运行。

**判据**：IDB 工具依赖 `@idasync` / `execute_sync()` 与 IDA 的 Qt 事件循环；`idat.exe` + 阻塞式 `-S` 脚本会让 IDB 调用挂死，`-S` 直接返回又会让端点退出。应使用 `ida.exe` 启动，脚本里后台 `serve()` 后及时 return，保活/清理放 daemon 线程。

**排除/降权**：`server_health` 能返回才说明端点活着；`tools/list`、`int_convert` 不依赖 IDB，不能作为 IDB 可用性的判据。

**操作要点**：先探活，再开库；批量 Hex-Rays 反编译可能卡 HTTP 线程，导出优先用纯反汇编。来源：旧 `tool-quirks` 的 IDA MCP 条目。

## 工具判据：localhost 代理劫持与 `--noproxy` 的边界

**适用**：从宿主访问本地 MCP/IDA/HTTP 端点，或访问外网下载站。

**判据**：本机代理可能劫持 localhost；对本地端点应显式 `curl --noproxy '*'`（或等价配置）。反过来，外网/archive 站点可能必须走代理；`--noproxy '*'` 不是万能，curl 000 时要在代理/直连之间做 A/B，再判断站点是否存在。

**排除/降权**：单次 000/超时不能推出“站点不存在/端点坏了”；先记录是否走代理、重试间隔和响应码。

**操作要点**：本地端点永久带 `--noproxy`；外网下载/查询记录代理路径与状态码。来源：旧 `tool-quirks` 的本机代理条目。
