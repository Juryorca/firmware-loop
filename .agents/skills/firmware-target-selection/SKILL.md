# 目标选择与固件获取

## 适用场景

- 新目标立项、在多个型号/版本间排序；
- 需要从厂商下载页、OTA、云存储或更新器中拿到固件；
- 判断"纯上游拼装"还是"厂商自研/改写/胶水层"。

## 选择因子

1. **厂商自研/改写量**：自研守护进程、插件、CGI/API 胶水层、权限映射优先；纯上游本体只做版本-CVE 排除。
2. **可达攻击面**：预认证、网络监听、代理型入口、封装应用优先。
3. **历史漏洞密度**：同厂商/同组件/同 SDK 的已公开案例只作排除与方向，不直接生成假设。
4. **补丁可及性**：能拿到相邻版本/补丁 diff 时优先；拿不到则降低结论强度。
5. **可复现性**：能在容器/仿真/提取镜像中建场；真机不是本工作区必需。

## 获取步骤

1. 记录来源 URL、文件大小、MD5/SHA256 到 `intel/firmware/<target>/SOURCE_URL.txt`。
2. 官网 JS 壳页面用无头浏览器 MCP 找真实下载 API；拿到直链后回到 `curl` 下载并校验。
3. OTA/云存储/更新器：先静态找 URL/签名/加密例程，再决定是否解包。
4. 提取：binwalk/unblob 两者产出都查；加密/非标格式按 `knowledge/tool-quirks` 的经验处理。
5. 建立 rootfs 工作副本，记录版本、架构、提取工具与失败原因。

## 判据与边界

- 不能因为“版本旧/有 CVE”直接判定漏洞；必须在本目标代码/行为上验证。
- 拿不到样本是具体外部阻塞时记录需求，不要用占位目标伪造研究。
- 历史 CVE 只进排除清单，不生成“没修完整”假设。

## 验收

- `SOURCE_URL.txt` 可重下（URL/大小/哈希）；
- 目标型号/版本/架构明确；
- 提取产物可复现，失败有原因。
